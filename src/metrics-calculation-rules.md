# Регламент автоматизированного расчёта метрик

## 1. Связанные документы и границы задачи

Ориентироваться на действующие `paper/experiment_protocol.md`, `paper/metrics.md`, `src/ai-judge-rules.md`, `data/dataset_schema.md`. Этот документ конкретизирует **технические правила вычисления** и согласованные решения руководителя. Он не заменяет научное обоснование метрик и не разрешает менять протокол оценивания.

Необходимо разработать **отдельный анализатор** результатов. Не добавлять расчёт метрик в существующий runner или адаптеры, не менять их промпты и логику обращения к API. Анализатор работает офлайн, только на сохранённых файлах. Никаких новых вызовов Qwen3.7 Flash/Clef и дополнительных расходов на API.


## 2. Интерфейс запуска

Предпочтительная точка входа:

```bash
python -m src.calculate_metrics --dataset main --run-id 005
python -m src.calculate_metrics --dataset pilot --run-id 003
```

- `--dataset` обязателен и принимает `smoke`, `pilot`, `main`.
- `--run-id` обязателен; анализируется **ровно один** явно выбранный пользователем запуск.
- Запуск ищется строго в `results/<dataset>/<run_id>/`, с учётом путей из `src/config.yaml`.
- **Автоматически искать последний запуск запрещено.** Не объединять разные `run_id`.
- Для `smoke` сразу выводить понятную ошибку «Smoke-запуски не поддерживают расчёт научных метрик» и завершать работу **без создания отчёта**. Этот режим остаётся разрешённым значением CLI, но не обрабатывается.
- Для `pilot` и `main` вычисления одинаковы; тип выборки ясно указывается в каждом отчёте. Пилотные результаты не представлять как результаты независимой тестовой выборки.
- Если выбранный каталог/нужный входной файл отсутствует или JSON невозможно прочитать, вывести понятную техническую ошибку и завершить работу. **Дополнительный этап проверки корректности датасета/голосов не реализовывать:** данные уже проверяются предыдущими этапами.

## 3. Источники и сопоставление данных

**Исходные файлы:**

1. `metadata.json` — идентификатор и режим запуска, выбранные поединки (`selected_bout_ids`), модели, параметры и плановые задания (`planned_tasks`).
2. `calls.jsonl` — фактически полученные голоса и вероятности моделей, технические ошибки, ревизии заданий.
3. Текущие JSON-транскрипции **указанной** выборки (`data/pilot_dataset/` или `data/dataset/`, либо пути из конфигурации) — `id` и `human_votes` для выбранных в `metadata.json` поединков. Использовать только `selected_bout_ids`, а не весь каталог как знаменатель метрик.
4. `summary.json` допустимо использовать для технической справки, но **не считать его источником научных голосов**; главный источник — `calls.jsonl`.

Связать исходные данные по полю `id` поединка, а не по имени файла. Три коллегии в результатах имеют машинные ключи `hiring`, `negotiation`, `ownership`; соответствующие названия в `human_votes` — «Нанимающаяся на работу», «Отправляющая на переговоры», «Доверяющая собственность».

Для каждого ключа `(run_id, model_alias, bout_id, variant, collegium, repeat_index)` учитывать **только последнюю сохранённую ревизию** из `calls.jsonl`. Более ранние ошибки и технические попытки не являются дополнительными голосами. Использовать `response.winner` только у записей со `status="success"`; `response.probabilities` (если присутствует) — исключительно как реальные вероятности провайдера. `raw_response`, `attempts`, `usage` не подменяют нормализованный голос.

Входной датасет использовать **в текущем состоянии**. Не сравнивать его с версией на момент запуска оценивания и не дорабатывать runner для записи хешей. Для всех реально использованных входных файлов сохранять SHA-256 (см. § 10). Отмечать в отчёте ограничение: эти хеши сами по себе не подтверждают, что в момент оценивания использовался идентичный текст транскрипций.

## 4. Единицы анализа и полнота

**Единица основного сравнения:** `поединок × коллегия`. На полном поединке у каждой модели три коллегии, по три повторных голоса в каждой: **9 голосов для `original`**. Человеческая коллегия имеет **3 голоса**.

- **Полный `original`-поединок модели:** успешны все 9 плановых голосов этого `bout_id × model_alias × original`. Если успешных голосов меньше девяти, **весь поединок исключается из всех основных метрик данной модели**, даже если часть коллегий полная. Не рассчитывать основные метрики по остаточным коллегиям.
- **Полный `swapped`-поединок модели:** успешны все 9 голосов варианта `swapped`.
- Основные метрики согласованности с людьми используют **только полные `original`**. Неполный или отсутствующий `swapped` **не исключает** полный `original` из этих метрик.
- Метрики позиционной чувствительности используют **только поединки, полные одновременно в `original` и `swapped`** для данной модели. Другие поединки из этой метрики исключаются отдельно.
- Для вероятностных метрик нужна полная тройка **реальных вероятностей** в конкретной коллегии сверх условия полного `original`. Если хотя бы в одном из трёх вызовов вероятности нет — данная коллегия исключается **только** из Brier Score и Vote Share MAE. Её голосования остаются пригодными для непрерывностных/классификационных метрик.
- Не восстанавливать, не прогнозировать и не подставлять недостающие голоса или вероятности. Не считать отдельные повторы ИИ независимыми экспертами или независимыми единицами выборки.
- Для каждой метрики сохранять собственный знаменатель и причину исключения. `N_bouts` — число независимых кластеров-поединков; `N_cases` — число использованных записей «поединок × коллегия» с учётом сравниваемых моделей; `N_model_votes` и `N_human_votes` — фактическое число голосов соответствующего источника, вошедших в расчёт; `N_comparisons` — число элементарных сопоставлений, которое не является числом независимых наблюдений. Для probability coverage `N_model_votes` считает только голоса с доступной вероятностью. Неприменимый к метрике счётчик хранить как `null` в JSON и как пустое значение в CSV. Пустая выборка → `N/A` с объяснением, а не ноль.

Формировать и сохранять перечни успешных, неполных и исключённых поединков **по каждой модели и виду расчёта**. Для неполного запуска расчёт проводится по пригодной части, а не прерывается целиком.

## 5. Агрегирование голосов

Для каждой полной пары `поединок × коллегия` и модели:

- Собрать три голоса `original` в порядке `repeat_index = 1, 2, 3`.
- Посчитать голоса за `player_1` и `player_2`; определить победителя **по большинству** (возможны только `3:0` или `2:1`, ничьей нет).
- Аналогично определить победителя коллегии по трём соответствующим `human_votes`.
- Сохранить исходные три голоса, счёт, большинство модели и людей, факт совпадения; при наличии — три вероятности.
- В отдельном описательном блоке посчитать **общие 9 голосов** модели и девять человеческих голосов за каждый поединок, общего победителя по большинству (`5:4`, `6:3` и т. д.) и факт совпадения общих победителей. **Этот показатель не подменяет основную Accuracy по коллегиям.**

**Переобозначение игроков:** все голоса и вероятности `swapped` перед сопоставлением с `original` переводить обратно к исходным реальным игрокам. Смена метки при выборе того же реального участника не является сменой решения. Соответствие отдельных повторов `original #1` и `swapped #1` не считать соответствием судейских личностей.

Для `DecisionJudge` порядок игроков дополнительно канонизируется внутри адаптера до обращения к Clef. Поэтому его позиционные метрики описывают устойчивость **нормализованной системы**, включая канонизацию, и не являются измерением сырой чувствительности Clef к порядку меток. Это ограничение явно указывать при сравнении моделей.

## 6. Наборы поединков и правила сравнения моделей

Для каждого `run_id` выделять:

1. **Индивидуальная выборка модели `S_m`** — все поединки, у которых модель имеет полный `original`.
2. **Общая выборка `S_common`** — пересечение `S_m` всех участвовавших моделей.
3. **Выборка позиционного анализа модели `S_position,m`** — поединки с одновременно полными `original` и `swapped`.
4. Для непосредственного **сравнения позиционной чувствительности моделей** — пересечение их `S_position,m`.
5. **Вероятностная подвыборка** — пригодные пары `поединок × коллегия` с тремя реальными вероятностями, отдельно для каждого выбранного скоупа. Не расширять её за счёт неполных троек.

Рассчитывать метрики каждой модели как на **всех её пригодных поединках**, так и **на общей выборке**. Для сравнительных таблиц и разницы моделей брать только `S_common`: сравнение индивидуальных результатов на разных наборах не интерпретировать как честное сравнение качества. Если модель одна, сравнительный раздел пометить как неприменимый. Для каждого скоупа явно сохранять список `bout_id` и `N`.

**Human–Human Agreement** считать:
- на **всех `selected_bout_ids` запуска**, вне зависимости от статуса оценивания ИИ;
- на **каждой** индивидуальной выборке модели `S_m`;
- на **общей** выборке `S_common`, если в запуске несколько моделей.

Человеческую согласованность нельзя автоматически приравнивать к Agreement Rate модели: это показатели с разными процедурами сравнения.

## 7. Основные и дополнительные метрики

В формулах ниже `i` — пара `поединок × коллегия` из соответствующей полной выборки, `N` — количество таких пар (`N = 3 × N_bouts` для основных метрик), `h_i ∈ {0,1}` — индикатор большинства людей в пользу `player_1`, `m_i ∈ {0,1}` — индикатор большинства модели в пользу `player_1`.

### 7.1. Agreement Rate (Accuracy) — главная метрика

`Accuracy = (1/N) Σ_i 1[m_i = h_i]`.

Агрегировать **по парам «поединок × коллегия»**, а не по отдельным девяти голосам модели. Считать общий показатель и **Agreement by Collegium** для каждого из `hiring`, `negotiation`, `ownership`. При полном наборе у каждого поединка ровно три коллегии и одинаковый вес.

### 7.2. Cohen's Kappa

По двум векторам `m_i`, `h_i` на одной и той же выборке вычислить `κ = (p_o − p_e) / (1 − p_e)`, где `p_o` — наблюдаемое Agreement Rate, `p_e` — ожидаемое совпадение по эмпирическим маргинальным долям двух классов у модели и людей. Использовать метки `player_1`, `player_2`. Если знаменатель ноль или метрика математически неопределена — `N/A` + причина. Нельзя принудительно делать `κ=1` для случая, когда все наблюдения принадлежат одному классу у обоих оценщиков.

### 7.3. Individual Judge Agreement: два способа

**Основной — majority-to-individual.** Для каждой пары `i` сравнить `m_i` с **каждым из 3 человеческих голосов** той же коллегии. Усреднить долю совпадений по всем парам. Формально `(1/N)Σ_i [(1/3)Σ_{j=1}^3 1[m_i = human_vote_{ij}]]`.

**Дополнительный — all-pairs.** Для каждой пары `i` сравнить **каждый из трёх ответов модели** с **каждым из трёх голосов людей** (9 сравнений), вычислить локальную долю совпадений и усреднить по `i`. Формально `(1/N)Σ_i [(1/9)Σ_{r=1}^3 Σ_{j=1}^3 1[model_vote_{ir} = human_vote_{ij}]]`.

Не сопоставлять `repeat_index=1` с `judge_id=1` и т. д. Девять попарных сравнений не считать независимыми наблюдениями.

### 7.4. Human–Human Agreement: два способа

**Основной — pairwise agreement.** В каждой человеческой коллегии три голоса и три неупорядоченные пары судей: `(1,2)`, `(1,3)`, `(2,3)`. Локальная согласованность — доля совпавших пар. При `3:0` → `1`, при `2:1` → `1/3`. Итог — среднее по всем парам `поединок × коллегия` выбранного скоупа.

**Дополнительный — Fleiss' Kappa.** Каждый объект — `поединок × коллегия`. Строка матрицы — числа человеческих голосов за `player_1` и `player_2` (сумма = 3). Вычислить обычную Fleiss' κ с ожидаемым совпадением по наблюдаемым общим частотам классов; можно использовать `statsmodels.stats.inter_rater.fleiss_kappa(..., method="fleiss")`. **Не использовать Randolph/free-marginal κ под названием Fleiss.** Если формула не определена — `N/A` + причина.

### 7.5. Macro-F1

Использовать большинство модели (`m_i`) и большинство людей (`h_i`) с фиксированными двумя классами `player_1`, `player_2`. Для каждого класса вычислить precision, recall, F1; `Macro-F1 = (F1_player_1 + F1_player_2)/2`.

**Согласованное правило:** если хотя бы один из двух классов **отсутствует среди человеческих majority-labels** выбранной выборки, весь Macro-F1 помечать `N/A` с причиной, не заменять F1 отсутствующего класса нулём. Для остальных неопределённых случаев также `N/A`; не применять `zero_division=0` молча.

### 7.6. Repeatability / Consistency: два способа

По каждой полной тройке голосов модели в одной коллегии:

- **Unanimity Rate:** `1`, если все три голоса одинаковы (`3:0`), иначе `0` (`2:1`); итог — доля единогласных троек по всем `i`.
- **Pairwise Repeatability:** доля совпадающих пар из трёх пар ответов (`1` при `3:0`, `1/3` при `2:1`); итог — среднее по `i`.

Основной расчёт — на полном `original`; для `swapped` допустим **отдельный** диагностический расчёт на полных `swapped` с отдельным знаменателем. Не объединять два варианта в один показатель без отдельной подписи.

### 7.7. Position Bias: два способа

На `S_position,m`, отдельно по каждой коллегии, сравнивать исходное и **переведённое обратно к тем же реальным игрокам** переставленное оценивание:

- **Label Flip Rate:** `1`, если большинство модели после перестановки выбрало **другого реального игрока**, иначе `0`. Итог — доля смен победителя по парам `поединок × коллегия`.
- **Vote Share Change:** `|votes_original(player_1)/3 − votes_swapped_mapped_back(player_1)/3|` для каждой пары; итог — среднее. Результат находится в `[0,1]` и может отличаться от нуля даже без смены большинства.

Нельзя считать Label Flip Rate по несопоставленным меткам `player_1/player_2`. Результаты описывают чувствительность к перестановке, но не доказывают, что каждое различие обусловлено только позиционным смещением: учитывать Repeatability.

### 7.8. Brier Score — при наличии вероятностей

Для каждой пригодной пары `i` обозначить через `p_ir` **реальную вероятность выбора `player_1`** из `r`-го вызова Decision-модели, `r=1,2,3`. Цель — `h_i`: `1`, если большинство людей выбрало `player_1`, иначе `0`.

- **Основной вариант (по усреднённому прогнозу):** `p̄_i = (p_i1+p_i2+p_i3)/3`, затем `Brier = mean_i[(p̄_i − h_i)^2]`.
- **Дополнительный (по каждому прогнозу):** `Brier_individual = mean_i[(1/3)Σ_r(p_ir − h_i)^2]`.

**Не** использовать вероятность победителя модели вместо вероятности `player_1`: направление целевой переменной и вероятности должно совпадать.

### 7.9. Vote Share MAE — при наличии вероятностей

Пусть `v_i = human_votes_for_player_1 / 3` внутри человеческой коллегии.

- **Основной вариант:** `MAE = mean_i[|p̄_i − v_i|]`.
- **Дополнительный вариант:** `MAE_individual = mean_i[(1/3)Σ_r |p_ir − v_i|]`.

Оба вероятностных показателя считать только по парам с **тремя доступными провайдерскими вероятностями**. Для Qwen3.7 Flash, который возвращает только структурированный выбор без вероятностей, обе метрики — `N/A` с объяснением. Отсутствие вероятностей у Clef не делает его успешно полученный `winner` недействительным. Отдельно показывать `N` и coverage вероятностных метрик.

### 7.10. Описательные показатели

Помимо формальных метрик вывести по каждому поединку:
- человеческий счёт по коллегиям и общий счёт `9` голосов;
- счёт модели по коллегиям и общий счёт `9` голосов;
- совпадение большинства каждой коллегии;
- совпадение общих победителей по девяти голосам (доля таких совпадений — **вспомогательная описательная**, не основная Accuracy);
- распределения голосов `player_1/player_2` и характерные несовпадения, выявляемые по подробной таблице.

## 8. Доверительные интервалы и проверка H1–H3

**Принятый метод:** парный/кластерный percentile bootstrap по **целым поединкам**. Нельзя бутстрэпировать отдельные голоса или коллегии одного поединка как независимые объекты.

Технические настройки первой версии: `10_000` bootstrap-репликаций, воспроизводимый фиксированный seed `42`, двухсторонний **95% процентильный** доверительный интервал (`2.5-й`, `97.5-й` процентили).

1. Для **Agreement Rate отдельной модели** переотбирать с возвращением `N_bouts` целых поединков из её пригодной выборки. В каждом переотобранном поединке сохраняются **все три коллегии**. Пересчитывать Accuracy; брать процентили из 10 000 репликаций.
2. Для **разницы моделей** использовать **только `S_common`**. В каждой bootstrap-репликации переотбирать **один и тот же список целых поединков для обеих моделей**, затем считать `Δ = Accuracy_decision − Accuracy_llm`. Сохранить точечную разницу в процентных пунктах и 95% интервал той же разницы. Не рассчитывать разницу из независимо переотобранных выборок.
3. Тем же кластерным bootstrap построить индивидуальные CI для Cohen's κ, Pairwise Repeatability и Label Flip Rate, а также парные CI разностей моделей для Cohen's κ, Pairwise Repeatability и Label Flip Rate. Для κ исключать репликации, в которых знаменатель κ равен нулю, и сохранять `valid_replications`; если допустимых репликаций нет, интервал равен `N/A`.
4. Если при данных обстоятельствах интервал построить невозможно (например, нет пригодных наблюдений; либо менее двух независимых поединков), вывести `N/A` + причину. Для маленьких выборок давать предупреждение о ненадёжности интервальной оценки.
5. Отсутствие пересечения или одной из моделей делает соответствующий сравнительный интервал `N/A`, но индивидуальные показатели остаются.

### 8.1. Первичные перестановочные тесты

Уровень значимости `α = 0,05`. Единственное разрешённое семейство p-value состоит ровно из семи заранее заданных тестов: Accuracy и Cohen's κ для H1 отдельно у двух моделей, разница Accuracy для H2, разницы Pairwise Repeatability и Label Flip Rate для H3. Ко всему семейству применяется пошаговая коррекция Holm. Неприменимый тест сохраняется как `N/A`, считается запланированным членом семейства и не уменьшает множитель коррекции для остальных тестов.

1. **H1:** случайный уровень Accuracy равен `0,5`. Для каждой модели внутри каждого поединка одновременно сохранять либо инвертировать три majority-label коллегий и пересчитывать Accuracy/κ. Оба теста односторонние (`greater`). H1 решается отдельно по модели и подтверждается только при положительном направлении обоих эффектов и двух Holm-adjusted p-value `< 0,05`.
2. **H2:** на `S_common` переставлять местами полные блоки Decision/LLM отдельно внутри каждого поединка и пересчитывать `Accuracy_decision − Accuracy_llm`. Тест двусторонний. Разница κ имеет CI, но не входит в первичное семейство.
3. **H3:** аналогично выполнять двусторонние парные тесты разности Pairwise Repeatability на `S_common` и Label Flip Rate на `S_position_common`. H3 подтверждается, если значим хотя бы один из двух скорректированных тестов.
4. При `N_bouts ≤ 20` перечислять все `2^N` кластерных перестановок. При большем `N` выполнять `100 000` перестановок с seed `42`; Monte Carlo p-value считать как `(extreme + 1)/(B + 1)`.
5. Статусы итогов: `confirmed`, `not_confirmed`, `not_evaluable`. Последний используется, когда необходимые данные или определённая κ отсутствуют.

95% CI остаются описательными; формальные решения H1–H3 принимаются только по Holm-adjusted p-value. Эти процедуры не устраняют возможную нерепрезентативность датасета и не объявляют человеческие решения объективной истиной. Иные p-value или тесты превосходства без отдельного предварительного согласования запрещены.

## 9. Обработка неприменимости и ошибок

- При математически неопределённой метрике возвращать **`N/A` + пояснение**, а не `0`, `NaN`, `Infinity` или вымышленную вероятность.
- Специальные случаи: Cohen's κ или Fleiss' κ с нулевым знаменателем; Macro-F1 с отсутствующим человеческим классом; вероятностная метрика без полной тройки вероятностей; сравнительная метрика без пересечения выборок; CI при недостаточной выборке.
- **Разграничивать:** (а) техническая ошибка чтения/разбора, при которой расчёт завершается; (б) допустимая неполнота оценивания, при которой расчёт продолжается на пригодных данных; (в) математическая неприменимость отдельной метрики (`N/A`).
- Не запускать повторно имеющиеся тесты датасета и не вводить новый слой проверки бизнес-правил транскрипций или истории голосов; опираться на уже действующий контракт файлов. Допустимы необходимые технические проверки наличия и читаемости входов, а также подсчёт полноты **для определения знаменателей**.

## 10. Сохранение результатов, структура и повторный запуск

Каталог вывода: `results/<dataset>/<run_id>/metrics/`.

Выводить **краткую консольную сводку** и формировать минимум следующие файлы:

```text
metrics/
├── metrics.json              # Все значения, N, скоупы, доверительные интервалы, причины N/A
├── summary.csv               # Плоская таблица: модель × скоуп × метрика
├── by_collegium.csv          # Разбивка по трём коллегиям
├── per_bout_collegium.csv    # Каждая пара поединок × коллегия × модель с деталями
├── exclusions.csv            # Исключения, неполные блоки и причины
└── report.md                 # Понятный человеку отчёт для команды «Статья»
```

**`metrics.json`:** структурированные поля `run_id`, `dataset`, дата/время расчёта, `calculation_rules_version`, метод и настройки bootstrap, модели и их метаданные, файлы/хеши входов, скоупы и списки `bout_id`, значения метрик, `N`, CI, `status` (`ok`/`not_applicable`) и `reason` при `N/A`, перечни исключений. Секция `inference` содержит настройки перестановок и Holm, семь первичных тестов, расширенные CI и решения H1–H3. Недоступные числовые значения сериализовать как JSON `null` вместе с `status/reason`; `NaN`/`Infinity` запрещены.

**`summary.csv`:** поля уровня `model_alias`, `scope` (`individual`, `common`, `all_humans`, `position` и т. п.), `metric`, `value`, `N_bouts`, `N_cases`, `ci_lower`, `ci_upper`, `status`, `reason`; для первичных тестов дополнительно `hypothesis_id`, `test_id`, `alternative`, raw/adjusted p-value и решение. Для метрик сравнения использовать идентификатор пары фактических моделей. CSV сохранять в UTF-8 с заголовками, пригодными для pandas/Excel.

**`per_bout_collegium.csv`:** `run_id`, `dataset`, `bout_id`, `model_alias`, `collegium`, `original_status`, `swapped_status`, три человеческих голоса, три голоса модели `original`, счёт и большинство, совпадение, вероятности при наличии, результаты `swapped` **после обратного сопоставления** меток, изменение большинства/доли голосов, причины исключения. Данные неполных блоков показывать для диагностики, **не включать** в основные агрегаты.

**`by_collegium.csv`:** Agreement Rate и другие уместные показатели по каждой из трёх коллегий отдельно, с явными `N` и скоупом.

**`exclusions.csv`:** `bout_id`, `model_alias`, `variant`, `collegium` (если применимо), `metric_scope`, `reason`, фактическое/требуемое число голосов или вероятностей. Сохранять и случаи, когда `original` полный, но `swapped` неполон (исключение только из position-анализа).

**`report.md`:** краткая информация о запуске, составе выборки, количестве пригодных поединков, основная и сравнительная таблицы, отдельная таблица проверки H1–H3 с эффектами, CI, raw/adjusted p-value и нейтральными решениями, согласованность людей на трёх видах выборок, разбивка по коллегиям, устойчивость, позиционная чувствительность, вероятностные метрики/coverage, общие победители по девяти голосам, объяснения `N/A`, проблемы и ограничения интерпретации. Ссылаться на подробные CSV вместо вставки всех транскрипций и сырых ответов в Markdown.

**Повторный расчёт:** при повторном выполнении той же команды **автоматически перезаписывать только созданные файлы внутри `metrics/`**. `metadata.json`, `calls.jsonl`, `summary.json`, `run.log`, исходные JSON датасета не изменять. Желательно атомарно публиковать согласованный набор файлов, чтобы при ошибке записи не осталось частично нового отчёта. Не сохранять историю версий расчёта в новых вложенных каталогах.

Фиксировать точное время расчёта (UTC ISO 8601), **версию регламента/алгоритма**, параметры генерации CI и SHA-256 `metadata.json`, `calls.jsonl` и всех использованных файлов транскрипций. Одинаковые входы и версия алгоритма должны давать одинаковые **числовые значения** метрик и интервалов; время расчёта закономерно отличается.

Графики (PNG, SVG, PDF и т. п.) **не строить**. Предоставленных JSON/CSV достаточно, чтобы команда «Статья» могла подготовить их самостоятельно.

## 11. Организация кода

Разработчики сами выбирают модульную структуру, но рекомендуется разделить:

- чтение сохранённого запуска и сопоставление с `human_votes`;

- чистые функции расчёта метрик;
- bootstrap и сравнение моделей на парных данных;
- сериализацию JSON/CSV/Markdown и краткий консольный вывод.

Не дублировать логику онлайн-оценивания и не менять `src/run_experiment.py`, `src/judges/*`. Для вычислений допустимы стандартная библиотека, NumPy/pandas/scikit-learn/statsmodels при необходимости; новые зависимости явно добавить в `requirements.txt`. Запуск должен быть возможен без API-ключей и сети.

## 12. Минимальные тесты расчётного кода

Это **тесты нового анализатора**, а не повторная проверка качества датасета.

1. **Agreement Rate:** два поединка × три коллегии, заранее известное число совпадений; правильный знаменатель `6`, не `18`.
2. **Неполный `original`:** `8/9` голосов исключает **весь** поединок из основных метрик данной модели; другая модель на нём может оставаться пригодной.
3. **Неполный `swapped`:** полный `original` остаётся в основной Accuracy, но не участвует в Label Flip Rate.
4. **Ревизии:** неудачная ранняя ревизия и успешная поздняя считаются **одним** успешным плановым голосом.
5. **Сопоставление игроков:** при обмене `player_1` ↔ `player_2` и сохранении выбора того же реального человека Label Flip Rate равен нулю.
6. **Repeatability/Human–Human:** для `3:0` оба соответствующих показателя = `1`; для `2:1` pairwise = `1/3`, unanimity = `0`.
7. **Individual Judge:** в примере `human=[1,1,2]`, `model=[1,1,2]`: majority-to-individual = `2/3`, all-pairs = `5/9`.
8. **Вероятности:** на тройке `p=[0.8,0.6,0.7]`, `human_votes_for_1=2`, `human_majority=1`: основной Brier `0.09`, дополнительный Brier `0.096666...`; основной MAE `|0.7−2/3|≈0.033333...`, дополнительный MAE `≈0.077777...`. При отсутствии одной вероятности обе вероятностные метрики для пары `N/A`, а голосование остаётся пригодным.
9. **Human–Human скоупы:** полный набор, индивидуальные наборы моделей и их пересечение имеют правильные и разные знаменатели.
10. **Сравнение моделей:** берётся только пересечение успешно оценённых поединков; парный bootstrap переотбирает одинаковые `bout_id` для обеих моделей; фиксированный seed даёт воспроизводимый результат.
11. **N/A:** для отсутствующего человеческого класса Macro-F1 — `N/A`; неопределённая κ — `N/A` с причиной; в JSON числовое поле — `null`, не `NaN`.
12. **CLI и файлы:** `--dataset smoke` выдаёт ошибку без отчётов; явный `--run-id` обязателен; повторный расчёт заменяет только `metrics/`; скрипт работает без API-ключей.
13. **H1–H3:** проверить односторонние H1, парные двусторонние H2/H3, точное перечисление и Monte Carlo режим, коррекцию Holm по фиксированному семейству из семи тестов, `N/A` для неопределённой κ, воспроизводимость seed и сериализацию решений во все отчётные форматы.

## 13. Критерии готовности

Задача выполнена, если:

- запуск одной CLI-командой с выбором `pilot/main` и `run_id` даёт отчёт **из сохранённых оценок**, без обращений к моделям;
- реализованы все согласованные метрики и дополнительные варианты из § 7, с корректными скоупами и `N`;
- правильно исключаются неполные `original`, отдельно обрабатываются `swapped` и неполные вероятностные ответы;
- сравнение моделей производится на **общих** поединках, с парным bootstrap CI;
- сформированы семь заранее заданных перестановочных тестов, Holm-adjusted p-value и однозначные решения H1–H3;
- предусмотрены `N/A` с обоснованием и подробная диагностика по поединкам/коллегиям;
- сохраняются консольная сводка, JSON, CSV, Markdown; **без** графиков;
- не меняются исходные файлы и не выполняются новые вызовы API;
- тесты нового анализатора проходят, а команда «Статья» может восстановить таблицы результатов и проверить значения на уровне отдельных поединков.
