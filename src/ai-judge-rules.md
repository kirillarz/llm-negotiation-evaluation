# Технический регламент ИИ-оценщиков управленческих поединков

**Связанные документы:** `paper/experiment_protocol.md`, `data/dataset_schema.md`, `paper/metrics.md`

## 1. Назначение и границы документа

Документ задаёт техническое поведение системы, которая получает независимые голоса двух типов ИИ-оценщиков: обычной LLM и Decision-модели. Он определяет точки входа, ответственность модулей, формат их взаимодействия, выполнение вызовов, обработку ошибок, сохранение результатов и критерии готовности.

Методологические правила задаёт `paper/experiment_protocol.md`. Если этот документ и протокол расходятся, необходимо отдельно согласовать и документировать изменение; нельзя молча подменять методику технической реализацией.

## 2. Основные принципы

1. Существует **одна точка входа** — `src/run_experiment.py`, через которую запускаются обе модели.
2. Есть **два независимых адаптера**, расположенных в собственных каталогах: LLM и Decision. Они предоставляют одинаковый интерфейс, но самостоятельно формируют запросы к своим API и извлекают ответы.
3. **Общий Runner управляет** выборкой, поединками, коллегиями, повторами, исходным/переставленным вариантом и порядком запросов. Адаптер выполняет ровно **одно содержательное оценивание** при каждом обращении к его интерфейсу.
4. Обе модели получают **эквивалентную информацию о полном поединке**: без сокращения, пересказа или удаления раундов. Различия в техническом формате запросов допускаются.
5. Подготовка данных, перестановка меток, сохранение результатов и обработка технических сбоев выполняются централизованно.
6. По умолчанию содержательные запросы выполняются **последовательно**. Каждый голос получает одинаковые для своего условия данные, критерии и параметры, **без истории предыдущих голосов**.
7. Голоса человеческих судей никогда не передаются адаптерам и не используются при получении модельных ответов.
8. Результаты технического тестирования не смешиваются с результатами полноценного эксперимента.

## 3. Предлагаемая структура проекта

```text
src/
├── ai-judge-rules.md
├── config.yaml
├── run_experiment.py
├── experiment/
│   ├── runner.py           # Очерёдность задач и вызов адаптеров
│   ├── data_loader.py      # Загрузка, валидация, подготовка и swap
│   ├── storage.py          # Запись и возобновление запусков
│   └── schemas.py          # Контракты входов, ответов и статусов
└── judges/
    ├── base.py             # Общий интерфейс адаптера
    ├── llm/
    │   └── judge.py        # Обычная LLM
    └── decision/
        └── judge.py        # Decision-модель

prompts/
├── common/                 # Единые содержательные критерии коллегий
├── llm/                    # Технические шаблоны LLM
└── decision/               # Технические шаблоны Decision

results/
├── smoke/                  # Технические проверки
├── pilot/                  # Пилотные эксперименты
└── main/                   # Основные эксперименты
```

Это целевая логическая структура. Перенос существующих исходников выполняется разработчиками без необходимости переписывать работающие API-клиенты с нуля. Имена вспомогательных файлов допустимо уточнить при реализации, не меняя описанных контрактов.

## 4. Конфигурация и модели

- Настройки эксперимента хранятся в **одном `src/config.yaml`**, с независимыми разделами для LLM и Decision.
- Секреты API загружаются из переменных окружения / локального `.env`; в конфигурацию и результаты **не записываются**.
- **Рабочие модели:** LLM — `Qwen3.7 Flash`; Decision — `Clef`. Обе модели вызываются через AITunnel.
- **Финальная LLM:** `Qwen3.7 Flash`.

## 5. Запуск программы

Единая точка входа поддерживает выбор:

- модели: `llm`, `decision`, `all`;
- выборки: `pilot`, `main`;
- одного поединка по ID либо всей выбранной выборки;
- полного эксперимента либо `smoke`-теста;
- создания нового запуска либо возобновления существующего `run_id`.

**Предлагаемый CLI-контракт:**

```bash
python -m src.run_experiment --model llm --dataset pilot
python -m src.run_experiment --model decision --dataset pilot --bout-id 1
python -m src.run_experiment --model all --dataset main --confirm-main
python -m src.run_experiment --model llm --dataset pilot --bout-id 1 --smoke
python -m src.run_experiment --resume <run_id>
```

Названия CLI-флагов допускается уточнить при написании кода, но перечисленные возможности обязательны.

**`smoke`-режим:** один поединок, одна коллегия, один голос. Это проверка работоспособности, **не** полная экспериментальная серия. Такие результаты записываются отдельно и не используются в научном анализе.

**Защита основной выборки:** запуск с `--dataset main` требует явного подтверждения (`--confirm-main` или эквивалент). По организационному правилу основные эксперименты запрещены до утверждения выборки, моделей, промптов и параметров. Сам флаг подтверждения не заменяет такое утверждение.

## 6. Загрузка, проверка и подготовка данных

1. Источники: `data/pilot_dataset/` и `data/dataset/`; соответствие каталогов режимам `pilot`/`main` задаётся конфигурацией.
2. Перед **любыми API-вызовами** выполняется строгая валидация **всех выбранных входных JSON** по текущей схеме и согласованным проверкам датасета.
3. Если хотя бы один выбранный файл невалиден, запуск останавливается **до первого запроса к API**; ошибки показываются пользователю.
4. После валидации формируется изолированный объект `PreparedBout`, содержащий **только** разрешённую модельному оценщику информацию:
   - `situation`;
   - все `rounds[]` по порядку;
   - `round_id` каждого раунда;
   - `roles.player_1` и `roles.player_2` каждого раунда;
   - все `turns[]` по порядку, включая `turn_id`, `speaker`, `text`.
5. Входной `id` используется только для учёта задач/результатов и **не требует передачи в содержательном запросе к модели**.
6. Исходные `human_votes`, комментарии судей, `result.score`, сведения о человеческом победителе и технические метаданные **не входят** в `PreparedBout` и недоступны адаптерам.

### Перестановка игроков (`swapped`)

Для дополнительного эксперимента общий модуль создаёт второй вариант `PreparedBout`, меняя `player_1` ↔ `player_2` **во всех обозначениях говорящего и привязках ролей во всех раундах**. Исходный текст реплик, смысл ситуации, фактические действия и хронология не меняются. Исходный объект не мутируется.

Адаптер возвращает `winner` в обозначениях **того варианта**, который получил. Система сохраняет `variant: original | swapped`. Обратная привязка к первоначальному игроку выполняется **позже при анализе**, без необходимости делать это внутри оценщика.

## 7. Содержательные критерии и промпты

Используются три коллегии:

| Код | Коллегия | Судейский вопрос |
| --- | --- | --- |
| `hiring` | Нанимающиеся на работу | К кому из игроков я пошёл бы работать? |
| `negotiation` | Отправляющие на переговоры | Кого из игроков я отправил бы вместо себя на важные переговоры? |
| `ownership` | Доверяющие собственность | Кому из игроков я доверил бы собственность или ресурсы? |

Единые содержательные критерии хранятся в `prompts/common/`. LLM- и Decision-адаптеры могут иметь собственные технические шаблоны запросов, но не должны вводить разные судейские критерии или давать одной модели дополнительные сведения о поединке.

Каждый содержательный вызов задаёт **ровно одну коллегию** и требует **ровно одного голоса**: `player_1` или `player_2`, без ничьей и отказа. Текстовое обоснование **не требуется**. Нельзя добавлять искусственные «личности» трём повторным голосам одной коллегии.

## 8. План одного полного оценивания

Для **каждой выбранной модели** и **каждого поединка**:

1. `original`: коллегия `hiring` — 3 отдельных вызова; `negotiation` — 3; `ownership` — 3.
2. `swapped`: те же три коллегии и по три независимых вызова на переставленном варианте.
3. Итого **18 содержательных голосов на одну модель и один поединок** (9 исходных + 9 переставленных).
4. Если выбраны обе модели, на один поединок запланировано **36 содержательных голосов** без учёта технических повторных попыток.
5. Внутри каждой комбинации `(поединок, модель, вариант, коллегия)` три повтора получают **одинаковый** вход, промпт и эффективные параметры; ответы предыдущих запросов в новый запрос не включаются.
6. Все задания имеют устойчивый ключ `(run_id, model_alias, bout_id, variant, collegium, repeat_index)` с `repeat_index ∈ {1,2,3}`. Один ключ соответствует **одному плановому голосу**; технические попытки относятся к этому же ключу.

Голоса не агрегируются и не сравниваются с решениями людей на стадии сбора. Сохраняются все отдельные результаты для последующего анализа.

## 9. Единый контракт адаптера

Каждый адаптер предоставляет метод с логикой:

```python
response = judge.evaluate(
    bout=prepared_bout,
    collegium="hiring",
)
```

Один вызов `evaluate()` — **одно содержательное оценивание / один голос**. Runner передаёт адаптеру подготовленный поединок нужного варианта и код коллегии. Историю предыдущих вызовов адаптер не использует.

**Единый нормализованный успешный результат (`JudgeResponse`):**

```json
{
  "winner": "player_1",
  "probabilities": null,
  "raw_response": {},
  "usage": null
}
```

- `winner` обязателен и строго равен `player_1` или `player_2`.
- `probabilities` необязателен; если возвращён, содержит реальные значения провайдера для обоих игроков, а не вычисленные догадки.
- `raw_response` — доступный сырой ответ API, сохраняемый без потери значимых данных и **без секретов**.
- `usage` — статистика использования API, если доступна; если сведений нет — `null`.
- На `LLMJudge` и `DecisionJudge` распространяется **один контракт**. Различия API скрыты внутри адаптеров.
- `LLMJudge` и `DecisionJudge` перед отправкой строят канонический порядок игроков из полного набора их ролей и реплик. Поэтому `original` и `swapped` передаются Qwen и Clef в одинаковом смысловом порядке, а победитель и вероятности затем переводятся обратно в метки входного варианта. Поле `raw_response._adapter.canonical_labels_swapped` фиксирует факт такого преобразования.
- При ошибке адаптер сообщает о сбое вызывающему коду; Runner регистрирует технические попытки и итоговый статус. Ошибка **не подменяется голосом**.

Runner/Storage добавляют к ответу `run_id`, `bout_id`, `model_alias`, известные модель/версию/провайдера, `variant`, `collegium`, `repeat_index`, эффективные параметры, временные метки, статус и историю технических попыток. **Полный отправленный запрос или копия транскрипции в результаты не записывается.**

## 10. Ошибки и технические попытки

- На один плановый голос разрешены **до двух технических попыток в рамках обычного выполнения**: первая попытка и максимум один повтор с **теми же входом, промптом и настройками**.
- Временные ошибки API (например, 429, 5xx, timeout) допускают повтор. Некорректные ответы или нарушения схемы явно отмечаются; повтор, если он технически допустим, входит в тот же лимит.
- Конфигурационные ошибки (неверный/отсутствующий ключ, неподдерживаемая модель и т. п.) не ретраятся: соответствующий запуск прекращается с диагностикой.
- Если после разрешённых попыток валидный голос не получен, сохраняется запись со статусом `failed`, `winner: null`, описанием ошибки и историей попыток.
- После отдельного окончательного сбоя Runner может продолжать остальные задания; никаких недостающих голосов не додумывается.
- Успешный голос запрещено повторно запрашивать ради другого результата либо лучшего совпадения с человеческими оценками.
- Таймаут не доказывает, что сервер не выполнил запрос: дополнительное обращение к API может быть платным. Этот риск учитывается в журнале попыток.

## 11. Сохранение и возобновление

На каждый запуск создаётся уникальный `run_id` и каталог вида:

```text
results/pilot/<run_id>/
├── metadata.json     # Режим, выборка, выбранные модели, параметры, версии/пути промптов
├── calls.jsonl       # Одна запись на плановый голос с итогом и попытками
└── summary.json      # Только техническая статистика выполнения
```

Аналогично используются `results/main/` и отдельный `results/smoke/`.

`run_id` — общий для всех трёх каталогов порядковый номер с минимальной шириной
три цифры: `001`, `002`, …, `999`, `1000`. Следующий номер определяется по
максимальному числовому имени каталога сразу в `results/smoke/`,
`results/pilot/` и `results/main/`; устаревшие и посторонние нечисловые имена
при этом игнорируются. Поэтому `--resume <run_id>` однозначно находит запуск
независимо от его режима.

**Содержимое файлов:**

- `metadata.json`: идентификатор запуска, режим, выбранные входные ID, выборка, модели, провайдеры, доступные версии, эффективные настройки, идентификаторы/пути применённых промптов, время начала.
- `calls.jsonl`: по одной записи **на плановый голос**, с ключом задания, вариантом, коллегией, номером повтора, сырым ответом, нормализованным решением/дополнительными полями, статусом и попытками.
- `summary.json`: **только техническая полнота** (запланировано / успешно / ошибочно / осталось; статусы `original` и `swapped` по каждой модели и поединку, причины технических сбоев). **Без** подсчёта победителей, голосов по игрокам, метрик и сравнений с людьми.

Сохранение происходит **сразу после завершения каждого планового голоса** (успешного или неуспешного); уже записанные результаты не перезаписываются бесследно. Конкретный способ безопасной дозаписи и восстановления незавершённой строки JSONL выбирают разработчики.

При `--resume <run_id>` программа считывает ранее сохранённые записи и продолжает **только ещё не предпринимавшиеся** плановые голоса. Успешные результаты не запрашиваются повторно; окончательно неудачные голоса автоматически тоже не повторяются. Для нового ручного обращения к неудачным голосам предусматривается **явный параметр** (например, `--retry-failed`);

При возобновлении Runner проверяет, что явно записанные модель, выбранная выборка и параметры не отличаются от текущих. **Полная копия API-запросов и хеши входных данных/промптов не обязательны**; неизменность содержимого промптов и датасета после утверждения контролируется организационно.

## 12. Технические статусы

Для каждого планового голоса:

- `success` — получен и проверен один допустимый `winner`;
- `failed` — после допустимых технических попыток валидного голоса нет;
- `pending` — задача ещё не выполнялась (состояние планировщика, не обязательно отдельная строка JSONL).

Для каждого блока из **9 плановых голосов** (`bout_id × model × variant`):

- `completed` — все 9 голосов успешно получены;
- `partial` — есть хотя бы один успешный голос, но не все 9;
- `failed` — ни одного успешного голоса после попыток либо все задачи завершились ошибкой; различие с ещё не начатым блоком определяется количеством `pending`.

Для полного поединка обе части (`original` и `swapped`) учитываются **раздельно**. Выполнение полного протокола для модели и поединка считается завершённым, только если обе части `completed`.

Эти статусы отражают лишь **техническую полноту**, а не качество оценок.

## 13. Отдельный последующий этап анализа

Анализатор, который разрабатывается **после получения оценок**, будет читать сохранённые `calls.jsonl`, исходные человеческие голоса и правила из `paper/metrics.md` / `paper/experiment_protocol.md`. Он рассчитает большинство в коллегиях, общий результат, согласованность с людьми, повторяемость и влияние перестановки меток.

**До разработки анализатора** Runner и адаптеры **не** читают человеческие голоса для сравнения, не рассчитывают распределения победителей, большинство или научные метрики. Отсутствие анализа в этом этапе — осознанная граница работ, а не утверждение, что анализ более не нужен для статьи.

## 14. Тестирование и критерии готовности

**Обязательные автоматические проверки (с моками API, без платных вызовов):**

1. Все выбранные JSON валидируются до начала API-запросов; при ошибке ни один запрос не сделан.
2. `PreparedBout` исключает `human_votes`, комментарии, итоговый счёт и остальные запрещённые поля.
3. Порядок раундов и реплик, их ID, текст и роль игрока передаются корректно, без сокращения.
4. Перестановка `player_1` ↔ `player_2` корректно меняет метки и роли без изменения текста реплик; исходный JSON не мутируется.
5. Runner формирует 9 вызовов исходного варианта и 9 переставленного на модель; в `smoke` только один вызов.
6. Для каждой коллегии три повтора не содержат истории предыдущих ответов и используют одинаковую конфигурацию.
7. Оба адаптера удовлетворяют одному контракту; `winner` строго валидируется; необязательные данные Decision не теряются.
8. Ошибки сохраняются, лимит обычных попыток равен двум, результаты успешно выполненных голосов не теряются.
9. `--resume` пропускает успешные и окончательно неудачные голоса; явный повтор неуспешных отмечается отдельно.
10. Пилотные, тестовые и основные результаты раздельны; `main` без подтверждения заблокирован.
11. По `calls.jsonl` можно однозначно восстановить технические итоги каждого планового голоса; не возникает неразличимых дубликатов задания.

**Интеграционная проверка:** минимум один реальный пилотный поединок успешно проходит полную последовательность вызовов через API каждой выбранной модели; результаты, ошибки и возобновление запуска проверяются на практике.
