# План реализации пайплайна сбора голосов ИИ-судей

## 1. Цель и границы

Цель реализации — создать воспроизводимый пайплайн, который через единую точку входа получает и сохраняет независимые голоса обычной LLM и Decision-модели по правилам `src/ai-judge-rules.md`.

В этот план входят:

- загрузка и строгая валидация выбранных поединков;
- подготовка разрешённого модельного входа и перестановка меток игроков;
- планирование голосов;
- вызовы `GigaChat-2-Pro` через GigaChat SDK и `Clef` через AITunnel;
- обработка ошибок и технических повторных попыток;
- немедленное сохранение результатов;
- продолжение прерванного запуска;
- `smoke`- и `dry-run`-режимы;
- автоматические тесты без платных API-вызовов и ручная интеграционная проверка на пилоте.

В этот план **не входят** агрегация голосов, сравнение с людьми, расчёт метрик, построение таблиц и графиков. Сбор голосов не должен читать человеческие оценки для анализа. Полный исходный JSON разрешено читать только валидатору; адаптеры получают исключительно `PreparedBout` с полями из белого списка.

## 2. Зафиксированные решения

- Единственная точка входа: `python -m src.run_experiment`.
- Пилотные модели:
  - LLM — `GigaChat-2-Pro` через GigaChat SDK;
  - Decision — `Clef` через AITunnel.
- Конкретная модель и её параметры задаются конфигурацией, а провайдерская логика скрыта за общим интерфейсом. Замена модели того же типа не должна требовать изменений в runner, загрузке данных или хранении.
- Пилотная выборка зафиксирована в `data/pilot_dataset/`, ID `1–5`.
- Основная выборка находится в `data/dataset/` и может пополняться до начала основного эксперимента. На момент запуска обрабатываются все выбранные файлы, найденные в каталоге; специальный механизм расширения уже начатого запуска не нужен.
- Основой общих критериев становятся существующие `prompts/pilot/hiring.txt`, `sending-to-negotiations.txt` и `trustee-of-property.txt`.
- При выборе нескольких моделей ошибка предварительной конфигурации хотя бы одной модели останавливает весь запуск до первого API-вызова.
- `smoke` требует явные `--bout-id` и `--collegium`, использует только `original` и выполняет один голос каждой выбранной модели. При `--model all` это два вызова.
- Обычный лимит — две технические попытки на один плановый голос: первоначальная и один повтор.
- `--retry-failed` дописывает в тот же запуск явно версионированную ревизию результата неудачного задания.
- Проверка случайного упоминания человеческих итогов внутри `situation` или реплик выполняется людьми до эксперимента. Код не ищет и не редактирует такие фрагменты автоматически.
- Нужен `--dry-run`, не выполняющий сетевые запросы и не создающий экспериментальные результаты.

Имена небольших вспомогательных модулей можно уточнить при реализации, но ответственность слоёв менять не следует. Текущие прототипы сохраняются до достижения функционального соответствия новым адаптерам.

**Результат этапа:** из валидного файла детерминированно создаются безопасные `original` и `swapped`, не содержащие человеческой разметки.

### Этап 4. Реализовать интерфейс оценщика и планировщик задач

- [ ] В `judges/base.py` определить общий интерфейс:

  ```python
  judge.evaluate(bout: PreparedBout, collegium: Collegium) -> JudgeResponse
  ```

- [ ] Один вызов `evaluate()` должен выполнять не более одного сетевого запроса и возвращать один голос либо типизированную ошибку. Адаптер не управляет повторами, вариантами, коллегиями, файлами и результатами.
- [ ] Добавить предварительную проверку адаптера: наличие секрета, обязательных настроек и поддерживаемого model ID без раскрытия значения ключа.
- [ ] Реализовать детерминированное построение задач в runner:
  - полный режим: `поединок × модель × 2 варианта × 3 коллегии × 3 повтора`;
  - 18 голосов на модель и поединок;
  - 36 голосов на поединок при `--model all`;
  - последовательный порядок выполнения;
  - устойчивый ключ `(run_id, model_alias, bout_id, variant, collegium, repeat_index)`.
- [ ] Для `smoke` требовать один `--bout-id` и одну `--collegium`, планировать только `original`, `repeat_index=1` и по одному заданию на выбранную модель.
- [ ] Гарантировать, что три повтора одной комбинации получают эквивалентные вход, промпт и эффективные параметры, не видят предыдущих ответов и не разделяют историю диалога.

**Результат этапа:** полный план эксперимента можно построить и проверить на поддельном адаптере без реального API.

### Этап 5. Реализовать надёжное хранение и возобновление

- [ ] Создавать новый `run_id` и нужный каталог только после успешной общей предварительной проверки.
- [ ] Хранить результаты раздельно:

  - `results/pilot/<run_id>/`;
  - `results/main/<run_id>/`.
- [ ] Атомарно создавать `metadata.json` с режимом, выбранными ID, моделями, провайдерами, доступными версиями, эффективными параметрами, путями промптов и временем начала.
- [ ] Не записывать секреты, полный отправленный запрос или копию транскрипции.
- [ ] После каждого законченного планового голоса немедленно дописывать JSON-строку в `calls.jsonl` и принудительно сбрасывать буфер на диск.
- [ ] В одной логической записи хранить итоговый статус, нормализованный ответ, безопасно сериализованный сырой ответ, `usage`, ошибку и историю максимум двух автоматических технических попыток.
- [ ] Безопасно обновлять `summary.json`, содержащий только технические количества и статусы, без подсчёта голосов по игрокам.
- [ ] При `--resume <run_id>` восстанавливать состояние по метаданным и последним ревизиям записей:
  - пропускать успешные задания;
  - по умолчанию пропускать окончательно неудачные задания;
  - продолжать только `pending`;
  - проверять совпадение выборки, моделей и эффективных параметров.
- [ ] Для `--retry-failed` дописывать новую различимую ревизию того же задания с `record_revision`, ссылкой на предыдущую ревизию и признаком ручного повтора. Никогда не изменять старую строку бесследно.
- [ ] Считать актуальным состоянием задания его последнюю валидную ревизию. Успешное задание не разрешать повторять через `--retry-failed`.
- [ ] Обнаруживать повреждённую или неполную строку JSONL и завершаться с диагностикой, а не молча терять состояние.

**Результат этапа:** прерванный процесс можно безопасно продолжить, а каждое действие и ручной повтор однозначно восстанавливаются из файлов запуска.

## 5. Критерии готовности реализации

Реализация сбора голосов считается готовой, когда одновременно выполнены следующие условия:

- обе выборки проходят единую производственную валидацию;
- любой невалидный выбранный файл останавливает запуск до первого API-вызова;
- общий код не зависит от конкретных классов GigaChat или Clef;
- каждый адаптер делает один независимый голос и возвращает единый контракт;
- полный запуск создаёт ровно 18 заданий на модель и поединок, `all` — 36;
- `smoke` с явными поединком и коллегией создаёт по одному заданию на модель только для `original`;
- `dry-run` полностью проверяет будущий запуск без сетевых запросов и результатов;
- все запросы последовательны, не используют историю и не получают человеческие оценки;
- на плановый голос выполняется не более двух автоматических технических попыток;
- каждый завершённый голос немедленно сохраняется, а прерванный запуск продолжается без повторения уже завершённых задач;
- ручной повтор ошибки сохраняется как различимая ревизия, не уничтожающая предыдущую запись;
- результаты `smoke`, `pilot` и `main` физически разделены;
- основной запуск технически невозможен без явного подтверждения;
- автоматические тесты проходят без реальных API;
- один пилотный поединок прошёл полную ручную интеграционную последовательность через обе модели.

После выполнения этих критериев можно отдельно планировать анализ сохранённых голосов. Он не должен добавляться в runner или адаптеры задним числом.
