# План разработки подсчёта метрик

## Исходная точка и границы

- В репозитории уже есть строгие схемы `RunMetadata`, `CallRecord` и транскрипций, конфигурация путей и append-only журнал ревизий. Отдельного анализатора метрик пока нет.
- Главный технический источник требований — `src/metrics-calculation-rules.md`; `paper/experiment_protocol.md`, `paper/metrics.md`, `src/ai-judge-rules.md` и `data/dataset_schema.md` задают научный и файловый контекст.
- Анализатор работает только с сохранёнными файлами одного запуска. Он не вызывает API, не меняет runner, адаптеры, промпты, датасет и исходные файлы запуска.
- Нельзя открывать запуск через `RunStorage.resume()`: этот метод обновляет `summary.json`. Нужен отдельный read-only путь чтения с повторным использованием существующих схем данных.
- До реализации сериализации согласовать и зафиксировать строку `calculation_rules_version` и правило её изменения при обновлении алгоритма.

## Фиксированная структура файлов

Создавать новые постоянные файлы только по этой структуре. Если во время разработки потребуется новый модуль или тестовый ресурс, сначала обновить этот план, чтобы разные агенты не создавали дублирующие решения.

```text
src/
├── calculate_metrics.py          # CLI: аргументы, коды завершения, вызов pipeline
└── metrics/
    ├── __init__.py               # Публичные константы, включая версию алгоритма
    ├── contracts.py              # Внутренние типы входов, скоупов, метрик и N/A
    ├── loading.py                # Read-only чтение запуска/датасета, ревизии, SHA-256
    ├── preparation.py            # Полнота блоков, swapped mapping, кейсы и скоупы
    ├── calculations.py           # Чистые функции всех метрик и описательных итогов
    ├── bootstrap.py              # Кластерные CI и парное сравнение моделей
    ├── reporting.py              # JSON, CSV, Markdown, консольная сводка
    └── pipeline.py               # Оркестрация полного расчёта и атомарной публикации

tests/
└── metrics/
    ├── conftest.py               # Синтетические транскрипции и каталоги запусков
    ├── test_loading.py           # Входы, последние ревизии, ошибки и хеши
    ├── test_preparation.py       # Полнота, swapped mapping, исключения и скоупы
    ├── test_calculations.py      # Формулы, знаменатели и случаи N/A
    ├── test_bootstrap.py         # Кластерный/парный bootstrap и воспроизводимость
    ├── test_reporting.py         # Схемы файлов, UTF-8 и атомарная перезапись
    └── test_calculate_metrics.py # CLI и сквозные сценарии без API-ключей
```

Существующие файлы, которые разрешено изменить:

- `README.md` — добавить инструкцию по запуску анализатора и описание отчётов.
- `requirements.txt` — менять только при обоснованном добавлении зависимости расчётного кода.
- `plan.md` — отмечать выполненные пункты и заранее фиксировать согласованные изменения структуры.

Файлы, создаваемые анализатором во время каждого запуска:

```text
results/<dataset>/<run_id>/
└── metrics/
    ├── metrics.json
    ├── summary.csv
    ├── by_collegium.csv
    ├── per_bout_collegium.csv
    ├── exclusions.csv
    └── report.md
```

## Этап 1. Контракты анализатора и CLI

- [ ] Создать отдельный пакет расчёта метрик и точку входа `python -m src.calculate_metrics`.
- [ ] Реализовать обязательные аргументы `--dataset {smoke,pilot,main}`, `--run-id` и поддержку пути к `src/config.yaml` для тестов и нестандартных окружений.
- [ ] Для `smoke` завершать работу понятной ошибкой до чтения запуска и без создания `metrics/`.
- [ ] Определить внутренние типы для нормализованного голоса, пары `поединок × коллегия`, скоупа, исключения и результата метрики (`ok` либо `not_applicable` с `value=null` и причиной).
- [ ] Зафиксировать константы алгоритма: версия правил, три коллегии, `10_000` bootstrap-репликаций, seed `42`, 95% percentile CI и соглашение о вычислении процентилей.

## Этап 2. Read-only загрузка и происхождение данных

- [ ] По конфигурации найти ровно `results/<dataset>/<run_id>/`; прочитать `metadata.json` и `calls.jsonl`, а отсутствие/нечитаемость/невалидный JSON оформить как техническую ошибку.
- [ ] Проверить соответствие `run_id` и режима выбранному каталогу, не искать последний запуск и не объединять запуски.
- [ ] Для каждого планового ключа оставить только последнюю ревизию; голос брать только из успешной записи `response.winner`, вероятность — только из `response.probabilities`.
- [ ] Найти текущие транскрипции выбранной выборки по полю `id` и загрузить `human_votes` только для `selected_bout_ids`; не использовать имя файла или весь каталог как знаменатель.
- [ ] Не запускать повторную бизнес-валидацию датасета и не использовать `summary.json` как источник научных голосов.
- [ ] Рассчитать SHA-256 для `metadata.json`, `calls.jsonl` и каждого фактически использованного файла транскрипции; сохранить путь и хеш для отчёта.

## Этап 3. Нормализация, полнота и скоупы

- [ ] Сгруппировать план и последние ревизии по модели, `bout_id`, варианту, коллегии и `repeat_index`; считать блок полным только при наличии всех ожидаемых успешных голосов `1..3` в каждой из трёх коллегий.
- [ ] Исключать поединок модели из основных метрик целиком при неполном `original`; неполный `swapped` исключать только из позиционного анализа.
- [ ] Для `swapped` вернуть победителей и вероятности к исходным реальным игрокам до любых сравнений с `original`.
- [ ] Отдельно определить `S_m`, `S_common`, `S_position,m`, общее пересечение позиционных выборок и вероятностные подвыборки с полной тройкой реальных вероятностей.
- [ ] Сформировать по каждой модели и виду расчёта списки пригодных и исключённых `bout_id`, причины и фактические/требуемые количества голосов или вероятностей.
- [ ] Не восстанавливать пропуски и не считать отдельные повторы независимыми наблюдениями.

## Этап 4. Агрегация на уровне кейса и поединка

- [ ] Для каждой пары `поединок × коллегия` сохранить три человеческих и три модельных голоса, счёт, большинство, совпадение и доступные вероятности.
- [ ] Для позиционного скоупа добавить mapped-back голоса `swapped`, смену реального победителя и изменение доли голосов за исходного `player_1`.
- [ ] Для каждого полного поединка посчитать описательные итоги по девяти голосам модели и людей и совпадение общих победителей, не подменяя ими основную Accuracy.
- [ ] Представить неполные блоки в диагностических данных, но не включать их в агрегаты соответствующих метрик.

## Этап 5. Чистые функции метрик

- [ ] Реализовать Agreement Rate в целом и по коллегиям, Cohen's Kappa и Macro-F1 по большинствам на уровне `поединок × коллегия`.
- [ ] Реализовать Individual Judge Agreement: основной majority-to-individual и дополнительный all-pairs без попарного связывания номеров повторов и судей.
- [ ] Реализовать Human–Human Agreement: pairwise agreement и Fleiss' Kappa на всех выбранных поединках, каждом `S_m` и `S_common`.
- [ ] Реализовать Repeatability: Unanimity Rate и Pairwise Repeatability по тройкам голосов модели.
- [ ] Реализовать Position Bias: Label Flip Rate и Vote Share Change на `S_position,m`; для честного сравнения моделей также использовать общее пересечение их позиционных выборок.
- [ ] Реализовать Brier Score и Vote Share MAE в основном и individual-вариантах только для кейсов с тремя реальными вероятностями; отдельно считать coverage.
- [ ] Для каждой метрики возвращать собственные `N_bouts`, `N_cases` и при необходимости `N_votes`; пустые и математически неопределённые случаи оформлять как `N/A` с причиной, без `NaN`/`Infinity`.
- [ ] Считать метрики модели отдельно на её `S_m` и на `S_common`; сравнительные выводы строить только по общим выборкам.

## Этап 6. Bootstrap и сравнение моделей

- [ ] Построить 95% CI для Agreement Rate кластерным bootstrap по целым поединкам, сохраняя три коллегии вместе.
- [ ] На `S_common` вычислить точечную разницу `Accuracy_decision − Accuracy_llm` в процентных пунктах и парный CI с одинаковой bootstrap-выборкой `bout_id` для обеих моделей; роли и алиасы взять из `models.decision`/`models.llm` конфигурации.
- [ ] Сделать результаты воспроизводимыми при seed `42`; не добавлять p-value и непредусмотренные тесты превосходства.
- [ ] Возвращать `N/A` для CI при числе независимых поединков меньше двух, отсутствии модели или пересечения; для малых выборок добавлять предупреждение.
- [ ] При единственной модели помечать сравнительный раздел как неприменимый, не теряя её индивидуальные результаты.

## Этап 7. Формирование отчётов

- [ ] Создать краткую консольную сводку и обязательный набор файлов: `metrics.json`, `summary.csv`, `by_collegium.csv`, `per_bout_collegium.csv`, `exclusions.csv`, `report.md`.
- [ ] В `metrics.json` сохранить метаданные запуска и моделей, UTC-время расчёта, версию алгоритма, настройки bootstrap, хеши входов, скоупы со списками `bout_id`, метрики, CI, знаменатели, статусы, причины `N/A` и исключения.
- [ ] Заполнить CSV стабильными UTF-8 заголовками и явными скоупами; не сериализовать нечисловые значения как числа.
- [ ] В `report.md` дать основные и сравнительные таблицы, человеческую согласованность, разбивку по коллегиям, устойчивость, позиционный анализ, вероятностный coverage, описательные итоги и объяснения исключений/`N/A`.
- [ ] Зафиксировать в отчёте ограничения: `pilot` не является независимой тестовой выборкой; люди не объявляются объективной истиной; текущие хеши транскрипций не доказывают идентичность файлам на момент оценивания; position bias интерпретируется вместе с repeatability.
- [ ] Публиковать шесть файлов согласованно через временные файлы и атомарную замену; при повторном запуске заменять только эти файлы внутри `metrics/`, не удаляя посторонние файлы и не меняя источники.
- [ ] Не создавать графики и вложенные версии отчётов.
