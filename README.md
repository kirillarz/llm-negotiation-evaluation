## Автоматизированное оценивание управленческих переговоров с помощью LLM

Исследовательский проект команды студентов УрФУ, посвящённый изучению возможностей больших языковых моделей (LLM), в том числе моделей класса Decision, для автоматизированного судейства управленческих переговоров.

**Цель исследования** — определить, насколько оценки, выставляемые языковыми моделями на основе транскрипций реальных переговорных поединков, согласуются с оценками профессиональных судей, а также выявить характерные ошибки и ограничения такого подхода.

Репозиторий используется как единое хранилище исследовательских артефактов: материалов датасета, промптов, программного кода, результатов экспериментов и материалов для подготовки научной статьи.

## Сбор голосов ИИ-судей

Единая точка входа для Qwen3.7 Flash и Clef через AITunnel — `python -m src.run_experiment`. Для запуска нужен Python 3.11–3.13.

1. Создайте и активируйте виртуальное окружение, затем установите зависимости:

   ```powershell
   python -m venv .venv
   .\.venv\Scripts\Activate.ps1
   python -m pip install -r requirements.txt
   ```

2. Создайте `.env` из примера:

   ```powershell
   Copy-Item .env.example .env
   ```

   Обе модели используют один ключ AITunnel. Укажите его в `.env`, не добавляя файл в Git:

   ```dotenv
   AITUNNEL_API_KEY="ключ AITunnel"
   ```

3. Выполните нужную команду из корня репозитория:

   ```powershell
   # Проверить один поединок и план из 36 голосов без API-вызовов и записи результатов
   python -m src.run_experiment --model all --dataset pilot --bout-id 1 --dry-run

   # По одному голосу обеих моделей для одной коллегии (только original)
   python -m src.run_experiment --model all --dataset pilot --bout-id 1 --smoke --collegium hiring

   # Полный запуск обеих моделей для одного пилотного поединка
   python -m src.run_experiment --model all --dataset pilot --bout-id 1

   # Полный запуск на основной выборке после её организационного утверждения
   python -m src.run_experiment --model all --dataset main --confirm-main

   # Продолжить прерванный запуск
   python -m src.run_experiment --resume 005

   # Явно повторить только неудачные задания, сохранив прежние ревизии
   python -m src.run_experiment --resume 005 --retry-failed
   ```

`--model` принимает `llm`, `decision` или `all`. Для `--smoke` обязательны `--bout-id` и `--collegium`; допустимые коллегии — `hiring`, `negotiation`, `ownership`. Даже в режиме `--dry-run` выбранным адаптерам нужны соответствующие переменные окружения для проверки конфигурации.

### Результаты и коды завершения

Результаты разделяются по режимам: `results/smoke/<run_id>/`, `results/pilot/<run_id>/` и `results/main/<run_id>/`. Старые результаты прототипов хранятся отдельно в `results/legacy/` и не читаются новым runner.

Каждый новый запуск содержит четыре файла:

- `metadata.json` — параметры запуска, выбранные поединки, модели, промпты и план заданий;
- `calls.jsonl` — дополняемый журнал итогов и технических попыток каждого голоса; ручной повтор добавляется как новая связанная ревизия;
- `summary.json` — только технические количества `planned`, `success`, `failed`, `pending`, типы ошибок и состояния блоков, без агрегации победителей.
- `run.log` — человекочитаемый операционный журнал с ходом запуска, длительностями, ретраями и ошибками; ответы моделей, промпты, транскрипции и секреты в него не записываются.

Во время работы тот же операционный журнал выводится в терминал. Обычный прогресс
показывается по блокам `поединок × модель × вариант`; ошибки отдельных голосов и
повторные попытки появляются сразу. Например:

```text
2026-10-17T12:00:00Z INFO session.start run_id=005 action=new mode=pilot planned=60 selected=60 ...
2026-10-17T12:00:00Z INFO block.start block=1/20 bout=1 model=qwen3-7-flash variant=original tasks=3 manual_retries=0 request_timeout=2m00s max_attempts=2
2026-10-17T12:01:15Z INFO block.finish block=1/20 bout=1 model=qwen3-7-flash variant=original processed=3 success=3 failed=0 progress=3/60 percent=5.0 ...
2026-10-17T12:24:40Z INFO session.finish run_id=005 status=success success=60 failed=0 pending=0 elapsed=24m40s
```

При `--resume` новые события дописываются в существующий `run.log` и отделяются
новой парой `session.start` / `session.finish`; предыдущая история не
перезаписывается. Heartbeat внутри отдельного API-запроса не выводится: допустимое
время ожидания видно в `request_timeout` строки `block.start`.

Коды завершения:

- `0` — полный успех;
- `1` — есть неудачные или оставшиеся задания;
- `2` — ошибка аргументов, предварительной проверки, конфигурации или хранилища либо остановка из-за общей конфигурационной ошибки;
- `130` — прерывание с клавиатуры; сохранённые задания можно продолжить через `--resume`.

`test_run.py`, `src/models/baseline_llm.py` и `src/clef_decision_experiment/` — устаревшие прототипы, оставленные только для истории миграции. Для нового сбора голосов их использовать не следует.

## Офлайн-расчёт научных метрик

Анализатор рассчитывает метрики только по уже сохранённым результатам и текущим
транскрипциям: он не обращается к Qwen3.7 Flash, Clef или другим сетевым API. Для его
запуска достаточно Python 3.11–3.13 и зависимостей проекта; `.env` и API-ключи не
нужны:

```powershell
python -m pip install -r requirements.txt
```

Из корня репозитория явно укажите выборку и идентификатор ровно одного запуска:

```powershell
# Пилотная выборка
python -m src.calculate_metrics --dataset pilot --run-id 003

# Основная выборка
python -m src.calculate_metrics --dataset main --run-id 005
```

Анализатор ищет запуск только в `results/<dataset>/<run_id>/` с учётом путей из
`src/config.yaml`; последний запуск автоматически не выбирается, результаты разных
запусков не объединяются. `smoke` допустим как значение аргумента, но научные
метрики для него не рассчитываются. При нестандартном расположении конфигурации
можно передать `--config <путь-к-config.yaml>`.

После успешного расчёта в каталоге запуска появляется `metrics/` с шестью файлами:

- `metrics.json` — полный машиночитаемый результат: скоупы, значения, знаменатели,
  доверительные интервалы, причины `N/A`, исключения и SHA-256 входных файлов;
- `summary.csv` — плоская таблица «модель × скоуп × метрика»;
- `by_collegium.csv` — показатели отдельно по трём коллегиям;
- `per_bout_collegium.csv` — диагностические данные по каждой паре
  «поединок × коллегия × модель», включая неполные блоки;
- `exclusions.csv` — исключения из отдельных расчётов и их причины;
- `report.md` — краткий отчёт для команды «Статья» со ссылками на подробные CSV.

Повтор той же команды обновляет только эти шесть управляемых файлов. Он не меняет
`metadata.json`, `calls.jsonl`, `summary.json`, `run.log`, транскрипции и посторонние
файлы, добавленные командой в `metrics/`.

Результаты расчёта различают три ситуации:

- **техническая ошибка** — отсутствующий или нечитаемый вход, повреждённый JSON либо
  несогласованная история запуска; команда завершается с кодом `2` и не публикует
  новый отчёт;
- **допустимая неполнота** — части плановых голосов, `swapped`-ответов или
  вероятностей нет; расчёт продолжается на пригодных данных, а исключения и
  фактические знаменатели записываются в отчёты;
- **`N/A` отдельной метрики** — данных для её формулы недостаточно или она
  математически не определена; в JSON сохраняются `status: "not_applicable"`,
  `value: null` и причина, а не ноль, `NaN` или бесконечность.

Пилотный отчёт служит для проверки процедуры и не является результатом независимой
тестовой выборки. Полные правила расчёта описаны в
[`src/metrics-calculation-rules.md`](src/metrics-calculation-rules.md).

## Устаревший экспериментальный ноутбук GigaChat

Ноутбук `src/models/Untitled13.ipynb` оставлен для истории и не используется новым runner. Он поддерживает два способа получения старого ключа GigaChat:

- в интерфейсе Google Colab сначала используется Secret `GIGACHAT_CREDENTIALS`, а входной JSON выбирается через форму загрузки;
- при локальном запуске или работе с удалённым ядром вне интерфейса Colab ключ загружается из `.env`, а JSON — из пути `INPUT_JSON_PATH` (по умолчанию `data/dataset/fub_video_transcript.json`);
- если ни Colab Secrets, ни `.env` недоступны, ноутбук запрашивает ключ через скрытое поле только для текущего сеанса.

Локальный `.env` не передаётся в удалённое ядро автоматически. Удалённая среда должна видеть репозиторий и `.env`: синхронизируйте файлы, подключите Google Drive или разместите их в рабочем каталоге ядра. Сам `.env` уже исключён из Git и не должен попадать в репозиторий.

Если удалённое ядро не видит входной JSON, четвёртая ячейка покажет виджет загрузки. Выберите JSON, дождитесь появления имени файла в виджете и повторно запустите эту же ячейку.

## Структура репозитория

```text
.
├── data/             # Датасет и материалы для его подготовки
├── prompts/          # Инструкции и критерии оценивания для LLM
├── src/              # Python-код экспериментов и анализа
├── results/          # Обезличенные результаты, таблицы и графики
├── paper/            # Материалы и ссылки для статьи
├── requirements.txt  # Зависимости Python-проекта
└── README.md          # Описание репозитория
```

### `data/`

Описание датасета, схема данных, реестр источников и скрипты обработки.

### `prompts/`

Версии инструкций и критериев оценивания для LLM.

### `src/`

Python-код для запуска моделей, обработки данных и расчёта метрик.

### `results/`

Обезличенные результаты экспериментов, итоговые таблицы и графики.

### `paper/`

Ссылка на актуальный черновик статьи и подборка похожих статей.

## Зоны ответственности

- **Команда данных** — каталог `data/` и папка исходных материалов в облаке.
- **Команда ИИ** — каталоги `src/`, `prompts/` и `results/`.
- **Команда статьи** — каталог `paper/`.
