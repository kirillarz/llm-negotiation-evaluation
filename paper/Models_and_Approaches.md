## Models and Approaches

### Model Selection and Configuration

В исследовании сопоставлялись два способа автоматизированного оценивания управленческих переговоров: генеративный LLM-подход и специализированный Decision-подход. В качестве LLM использовалась модель `Qwen3.8 Flash` с API-идентификатором `qwen3.8-flash`; Decision-подход был реализован с помощью модели `Clef` с API-идентификатором `clef`. Обе модели вызывались через провайдера AITunnel, но через разные программные интерфейсы: Chat Completions API для Qwen и Decisions API для Clef. Такое построение позволяет сравнивать два практически различных режима решения одной задачи — генерацию строго структурированного ответа языковой моделью и нативный выбор из заданных альтернатив через специализированный интерфейс решений — при общем провайдере, одинаковом содержании переговоров и единых профессиональных критериях.

Термины «LLM-подход» и «Decision-подход» в работе обозначают прежде всего наблюдаемые способы обращения к моделям и получения ответа. Для использованных API-идентификаторов не были зафиксированы точные ревизии весов: поле `model_version` имело значение `null`. Материалы эксперимента также не позволяют достоверно установить архитектуру, число параметров, состав обучающих данных или процедуру обучения моделей. Поэтому различия между подходами далее описываются на уровне доступных API, форматов входа и выхода и фактически наблюдаемого поведения. Само использование разных интерфейсов не рассматривается как доказательство конкретных внутренних архитектурных различий.

Для `qwen3.8-flash` были заданы `max_tokens = 16` и объект `reasoning` со значениями `effort = none` и `exclude = true`; тайм-аут одного обращения составлял 120 секунд. Параметры `temperature` и `top_p` явно не задавались, поэтому их эффективные значения определялись стороной провайдера. Ограничение длины ответа соответствовало задаче бинарного выбора и не ограничивало длину входного контекста. В сохранённых ответах число reasoning-токенов было равно нулю. Для `clef` дополнительные параметры генерации не задавались, а тайм-аут также составлял 120 секунд. Конфигурация обоих адаптеров запрещала переопределять служебные поля запроса, формируемые программно.

Выбор моделей определялся одновременно исследовательской задачей и техническими ограничениями проекта. Использование управляемого API устраняло зависимость основного эксперимента от локальной GPU-инфраструктуры и позволяло провести полный объём повторных вызовов в ограниченные сроки. Доступ к обеим моделям через AITunnel также уменьшал инженерную неоднородность: использовались единый ключ и базовый адрес провайдера, общая схема обработки сетевых ошибок и единый механизм учёта токенов и стоимости, хотя сами конечные точки API различались.

Clef была выбрана как практически доступная реализация Decision-подхода. Decisions API непосредственно поддерживал передачу структурированного JSON в поле `state`, вопрос типа `choice` и получение выбранной альтернативы вместе с распределением вероятностей. Такой формат соответствовал постановке задачи, где требовался ровно один победитель, а вероятности могли использоваться для дополнительных метрик без извлечения оценок из свободного текста. Qwen3.8 Flash была выбрана как контрастный генеративный LLM-подход: модель была доступна у того же провайдера через совместимый с Chat Completions интерфейс, принимала полный текст поединка и поддерживала ограничение ответа строгой JSON-схемой. Вариант Flash позволял сформировать короткий структурированный ответ при отключённом reasoning-режиме и тем самым не требовал локального инференса или генерации развёрнутых объяснений.

Дополнительным основанием для выбора именно этой пары была их общая модельная линия. Согласно официальной карточке модели Cloudflare](https://huggingface.co/Cloudflare/clef), Clef получена путём дополнительного обучения (`post-training`) базовой модели `Qwen/Qwen3.8-27B`: к её backbone добавлена совместная головка схемы (`joint schema head`), оценивающая допустимые варианты типизированного решения. В [описании разработчиков](https://blog.cloudflare.com/clef-decision-models/) этот режим противопоставляется авторегрессионной генерации: после обработки контекста backbone-моделью специализированная головка параллельно присваивает оценки заранее заданным альтернативам, не формируя свободный текст ответа. Тем самым Clef сохраняет происхождение от семейства Qwen3.8, но адаптирована для непосредственного выбора по заданной схеме.

Вместе с тем использованную в исследовании Qwen3.8 Flash нельзя называть непосредственной базовой моделью Clef или вторым режимом тех же весов. Зафиксированная базовая модель Clef — `Qwen3.8-27B`, тогда как `qwen3.8-flash` представляет отдельную доступную через API генеративную модель из [линейки Qwen3.8](https://github.com/QwenLM/Qwen3.8). Следовательно, модели родственны на уровне модельного семейства, но не образуют контролируемую абляцию одной и той же модели. Такая связь делает пару содержательно релевантной для сопоставления традиционного генеративного оценивания и специализированного Decision-подхода при меньшей неоднородности происхождения, чем у полностью несвязанных моделей. Однако наблюдаемые различия нельзя приписывать исключительно головке решений или формату API: одновременно различаются базовые контрольные точки, последующее обучение и серверные реализации.

### Evaluation Approaches

Перед обращением к моделям исходный файл поединка преобразовывался в объект `PreparedBout`, сформированный по белому списку полей. Он включал описание ситуации, последовательность всех раундов, роли `player_1` и `player_2` в каждом раунде, номера реплик, обозначение говорящего и полный текст реплик. Идентификатор поединка использовался для организации экспериментальных заданий, но в содержательный вход модели не включался. Человеческие голоса, комментарии судей, итоговый счёт, метаданные источника и заранее известный победитель в объекте `PreparedBout` отсутствовали.

В LLM-подходе выполнялся POST-запрос к конечной точке `/v1/chat/completions`. Текст инструкции соответствующей коллегии передавался как системное сообщение. Пользовательское сообщение содержало полный сериализованный JSON поединка и краткое требование выбрать ровно одного игрока. Дополнительно использовался строгий `response_format` типа `json_schema`: ответ должен был быть объектом с единственным обязательным полем `choice`, принимающим значение `player_1` или `player_2`; дополнительные поля запрещались. Успешным считался только один ответ с `finish_reason = stop`, прошедший повторную валидацию локальной схемой. Нормализованным результатом становилось значение `choice`.

В Decision-подходе выполнялся POST-запрос к конечной точке `/v1/decisions`. Полный объект `PreparedBout` передавался в поле `state`. В поле `questions.vote` задавался вопрос типа `choice`; общий текст промпта соответствующей коллегии передавался как `instructions`. Для каждой альтернативы в `criteria` симметрично указывалось, что игрок может быть выбран только на основании действий, делающих его предпочтительным именно в заданной профессиональной перспективе, а номер метки, порядок предъявления и «общая победа» не являются критериями. Из ответа извлекалось нативное поле `answers.vote.choice`. Именно оно использовалось как бинарный голос Clef, а не результат повторного порогового преобразования вероятностей.

Clef также возвращала значения `answers.vote.probabilities` для `player_1` и `player_2`. Адаптер принимал их только как конечные числа в диапазоне от 0 до 1, сумма которых равна единице с допуском `10^-6`; распределение сохранялось вместе с голосом. Дополнительные поля провайдера, включая `confidence`, оставались в сыром ответе, но не подменяли нормализованный выбор. Таким образом, для обоих подходов основной результат одного вызова имел единый вид: обязательный `winner` и необязательное распределение `probabilities`. Различие форматов ответа отражает доступные интерфейсы моделей, но само по себе не позволяет делать выводы об их внутренних механизмах принятия решений.

### Prompt Design and Judging Perspectives

Использовались три отдельных содержательных промпта — по одному для каждой профессиональной судейской коллегии. Один и тот же текст соответствующего промпта применялся к обеим моделям; различались только техническое размещение инструкции в запросе и обязательные для Decisions API критерии альтернатив. Промпты не содержали примеров размеченных поединков или демонстраций правильных ответов. Поэтому подход является zero-shot оцениванием по явно сформулированным критериям, а не few-shot prompting.

Перспектива коллегии «Нанимающиеся на работу» задавалась вопросом о выборе руководителя, к которому судья предпочёл бы наняться. В центре оценки находились надёжность и ответственность, отношение к людям, управленческая твёрдость, а также забота о команде и организации. Коллегия «Отправляющие на переговоры» выбирала представителя для сложных переговоров; учитывались движение к цели, управление разговором, работа с интересами и ограничениями другой стороны и цена достигнутого результата. Коллегия «Доверяющие собственность» выбирала игрока, которому можно доверить ресурс; критериями служили качество решений, компетентность в исполняемой роли, ясность ответственности и сохранность ресурса с учётом экономических, юридических и репутационных рисков.

Все три промпта требовали оценивать поведение каждого реального игрока на протяжении всего поединка, учитывать смену игровых ролей между раундами и отдавать итоговый голос игроку, а не отдельному персонажу. Модель должна была выбрать ровно одного участника; ничья, отказ от ответа и оценивание только одного раунда не допускались. Промпты отдельно запрещали использовать привлекательность речи, исходную власть, выигрыш в торге, экономический результат или общую управленческую силу как самостоятельные основания, если они не относились к критерию конкретной коллегии. Текст транскрипции объявлялся материалом для анализа, а не источником инструкций для модели.

Для уменьшения зависимости от технических меток промпты прямо указывали, что `player_1` и `player_2`, порядок их размещения в JSON и порядок первого появления не свидетельствуют о качестве. Модели предписывалось выполнить два мысленных прохода сравнения в противоположном порядке, сопоставить выводы с конкретными действиями и последствиями, а затем применить контрфактическую проверку: при замене обозначений должен сохраниться выбранный человек и измениться только его техническая метка. Дополнительно подчёркивалось, что необходимо отвечать на вопрос конкретной коллегии, а не выбирать «общего победителя» поединка и не создавать искусственные различия между коллегиями.

Эти инструкции задают внутреннюю процедуру сравнительного анализа, однако в эксперименте не запрашивалось и не сохранялось пошаговое рассуждение. Qwen возвращала только короткий JSON, причём режим reasoning был отключён; Decisions API также возвращал структурированный выбор и вероятности без текстового обоснования. Следовательно, фактически реализованный метод нельзя описывать как наблюдаемый Chain-of-Thought prompting. Корректнее характеризовать его как zero-shot, rubric-guided pairwise evaluation со скрытой процедурной инструкцией и жёстко структурированным выходом.

### Evaluation Procedure

В основной процедуре оценивались 25 поединков. Для каждого поединка обе модели независимо применялись к трём судейским перспективам. Внутри каждой комбинации «поединок × модель × коллегия» выполнялись три вызова с одинаковыми входными данными, промптом и параметрами. Ответы предыдущих обращений не включались в последующие запросы, история диалога не поддерживалась, а каждый вызов создавал один самостоятельный голос. Повторения являются повторными измерениями одной модели, а не тремя различными искусственными судьями. Их независимость означает отсутствие передаваемого состояния на стороне экспериментального клиента; внутренняя обработка, кэширование и стохастичность сервиса провайдера исследователям недоступны.

Для каждой коллегии модельный победитель определялся большинством трёх голосов, поэтому возможны только результаты 3:0 и 2:1. Основной вариант входа дополнялся вариантом с перестановкой обозначений игроков. При его создании значения `player_1` и `player_2` менялись местами в описании ролей и в поле говорящего каждой реплики. Описание ситуации, текст реплик, номера и порядок раундов и реплик оставались неизменными. Канонизация порядка игроков внутри адаптеров и автоматическая коррекция возвращённого победителя не применялись.

На переставленном варианте повторялась та же схема из трёх коллегий и трёх вызовов. При последующем анализе каждый выбор `player_1` в переставленном варианте однократно отображался на исходного `player_2`, а `player_2` — на исходного `player_1`. Всего экспериментальный план включал `25 × 2 × 2 × 3 × 3 = 900` содержательных голосов: 450 на модель.

Каждое задание имело устойчивый ключ, включавший идентификатор запуска, модель, поединок, вариант входа, коллегию и номер повторения. На один плановый голос допускались не более двух технических попыток. Повтор выполнялся только после временной транспортной ошибки, ответа HTTP 429 или 5xx, тайм-аута либо ответа, не прошедшего проверку формата, и использовал тот же вход, промпт и параметры. Ошибки конфигурации прерывали выполнение, а постоянные транспортные ошибки не повторялись. Если после разрешённых попыток валидный ответ отсутствовал, сохранялась запись `failed` с `winner = null`; недостающий голос не заменялся и не выводился из остальных ответов. Успешный голос не запрашивался повторно из-за расхождения с человеческими оценками.
