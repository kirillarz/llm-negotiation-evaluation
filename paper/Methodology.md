## Experimental Design

Цель эксперимента — определить степень согласованности решений обычной LLM и Decision-модели с решениями профессиональных судей управленческих переговоров, сравнить два подхода между собой и оценить устойчивость их решений.

Модели рассматриваются исключительно как судьи: они не участвуют в переговорах и не генерируют стратегии для игроков. В каждом вызове модель должна выбрать одного из двух реальных участников переговорного поединка. Дополнительные числовые оценки навыков, отсутствующие в человеческой разметке, не используются.

## Dataset

Датасет включает **30 реальных управленческих переговорных поединков**, сформированных на основе видеозаписей турниров по управленческой борьбе (ФУБ). Для каждого поединка сохраняются описание исходной ситуации, оба участника (`player_1` и `player_2`), последовательность раундов, роли участников в каждом раунде, реплики и голоса профессиональных судей.

Каждый поединок состоит из **2–3 раундов** (в среднем 2.23). Среднее количество реплик на один раунд составляет **23.42**, минимальное — 3, максимальное — 42.

Подготовка данных включала автоматическое распознавание речи с помощью **Whisper base**, диаризацию говорящих, структурирование транскрипций с помощью **Qwen 2.5**, приведение файлов к единой JSON-схеме и автоматическую проверку структурных и логических ошибок. В данных могут сохраняться отдельные ошибки автоматического распознавания речи и диаризации, связанные с качеством исходных видеозаписей.

Выборка разделена на две части:
- **пилотная выборка — 5 поединков**, используемых для разработки, отладки и настройки пайплайна;
- **основная выборка — 25 поединков**, не использовавшихся при настройке и предназначенных для основного эксперимента и проверки гипотез.

## Professional Judging System

Оценивание проводится отдельно в рамках трёх профессиональных коллегий в соответствии с методикой Владимира Тарасова:

1. **Нанимающиеся на работу:** «К кому из игроков я пошёл бы работать?»
2. **Отправляющие на переговоры:** «Кого из игроков я отправил бы вместо себя на важные переговоры?»
3. **Доверяющие собственность:** «Кому из игроков я доверил бы собственность или ресурсы?»

Для каждой коллегии доступны три человеческих голоса. Каждый судья обязательно выбирает `player_1` или `player_2`; ничья не допускается. Обеим моделям задаются одинаковые по смыслу вопросы соответствующих коллегий.

## Models and Configuration

В эксперименте используются две модели, представляющие различные подходы к автоматизированному оцениванию:

- **LLM:** Qwen3.7 Flash (API model ID: `qwen3.7-flash`) — генеративная языковая модель, выполняющая оценивание через текстовые инструкции и возвращающая структурированный ответ.
- **Decision-модель:** Clef (API model ID: `clef`) — специализированная модель принятия решений, возвращающая выбор одного из заданных вариантов и вероятности выбора без необходимости генерировать текстовое обоснование.

Доступ к обеим моделям осуществляется через API-провайдера **AITunnel**. Для Qwen3.7 Flash используется эндпоинт `/v1/chat/completions`, для Clef — `/v1/decisions`.

В основном эксперименте использовались следующие параметры:

| Параметр | Qwen3.7 Flash | Clef |
|---|---|---|
| API model ID | `qwen3.7-flash` | `clef` |
| Провайдер | AITunnel | AITunnel |
| `max_tokens` | 16 | Не задаётся |
| `reasoning.effort` | `none` | Не задаётся |
| `reasoning.exclude` | `true` | Не задаётся |
| `temperature` | Не задаётся | Не задаётся |
| `top_p` | Не задаётся | Не задаётся |
| Таймаут запроса | 120 секунд | 120 секунд |

Параметры `temperature` и `top_p` для Qwen3.7 Flash явно не устанавливаются, поэтому используются значения, определяемые API-провайдером. Для Clef дополнительные параметры генерации не задаются.

**Форматы запросов и ответов моделей различаются:**

- **Qwen3.7 Flash** получает системный промпт и JSON-представление поединка через Chat Completions API. Используется `response_format` с JSON Schema, ограничивающей ответ объектом с единственным полем `choice`, принимающим значение `player_1` или `player_2`. Вероятности выбора игроков в эксперименте не запрашиваются и не используются.
- **Clef** получает JSON-представление поединка в поле `state` и вопрос судейской коллегии в объекте `questions.vote` с типом `choice`. Для каждого игрока задаётся соответствующий критерий выбора. API возвращает выбранного игрока в `answers.vote.choice` и может предоставлять распределение вероятностей `answers.vote.probabilities`.

Ответы обеих моделей приводятся к единому внутреннему формату, содержащему обязательное поле `winner` (`player_1` или `player_2`) и необязательное поле `probabilities`. Это обеспечивает сопоставимость бинарных решений моделей при расчёте основных метрик согласованности с профессиональными судьями.

Для воспроизводимости сохраняются идентификаторы моделей, провайдер, используемые параметры, промпты и сырые ответы API. **Точные идентификаторы версий (снапшотов) моделей в метаданных основного эксперимента не зафиксированы** (`model_version = null`), что является ограничением воспроизводимости при возможном обновлении моделей провайдером.

## Model Inputs and Prompts

В модель передаются только данные, необходимые для оценки поединка: описание ситуации, все раунды в исходной последовательности, роли обоих игроков, пронумерованные реплики и промпт соответствующей коллегии.

Человеческие голоса, комментарии судей, итоговый счёт и любая информация о победителе по человеческим оценкам не передаются модели и используются только после получения модельных ответов. Обе сравниваемые модели получают одинаковый по смыслу объём переговорной информации и обрабатывают полный текст поединка.

Для каждой из трёх коллегий используется отдельный промпт. В каждом случае модели явно указывается соответствующая перспектива: выбор руководителя, к которому судья предпочёл бы наняться; представителя для сложных переговоров; либо управляющего, которому можно доверить собственность или ресурс. Во всех промптах подчёркивается, что необходимо оценивать весь поединок, выбирать ровно одного игрока и не определять «общего победителя» вне заданной судейской перспективы.

## Main Experiment

Для каждой модели на каждом поединке основной выборки выполняются девять независимых вызовов:
- три вызова для коллегии «Нанимающиеся на работу»;
- три вызова для коллегии «Отправляющие на переговоры»;
- три вызова для коллегии «Доверяющие собственность».

Таким образом, каждая модель формирует девять модельных решений на один поединок. Три вызова внутри одной коллегии получают одинаковые транскрипт, промпт и параметры и не используют историю предыдущих ответов. Для обеих моделей модельным голосом считается возвращённое значение `winner`.

Повторные вызовы рассматриваются как повторные измерения одной модели, а не как независимые эксперты. Для каждой коллегии определяется модельный счёт 3:0 или 2:1 и победитель по большинству.

Основная единица сравнения — **пара «поединок × коллегия»**. Победитель по трём модельным голосам сравнивается с победителем по трём голосам профессиональных судей той же коллегии. Дополнительно анализируются агрегированный победитель по девяти вызовам и распределения голосов. Отдельные модельные вызовы не сопоставляются с конкретными человеческими судьями по порядковым номерам.

## Stability and Position Bias

Три вызова внутри каждой коллегии используются для анализа повторяемости решений модели. Отдельная серия повторов только ради проверки стабильности не проводится.

Дополнительно на всей основной выборке проводится эксперимент с перестановкой обозначений игроков. Для каждого поединка создаётся версия, в которой `player_1` и `player_2` меняются местами в обозначениях говорящих и в описании ролей, тогда как реальные участники, содержание реплик и хронология переговоров остаются неизменными.

На переставленной версии выполняются ещё девять вызовов каждой модели. При анализе ответы переводятся обратно к исходным реальным игрокам, поэтому смена обозначения при сохранении выбора того же человека не считается изменением решения. Эта серия используется для расчёта Position Bias / Label Flip Rate.

## Evaluation Metrics

Главной метрикой является **Agreement Rate (Accuracy)** — доля пар «поединок × коллегия», в которых победитель по большинству модельных голосов совпадает с победителем по большинству человеческих голосов.

Для интерпретации используются **Cohen's Kappa**, **Individual Judge Agreement**, **Human–Human Agreement** и **Agreement by Collegium**. Дополнительно рассчитывается **Macro-F1**.

Устойчивость решений оценивается через **Repeatability / Consistency**, а чувствительность к позиции игроков — через **Position Bias (Label Flip Rate)**.

Если Decision-модель возвращает реальные вероятности выбора игроков, дополнительно рассчитываются **Brier Score** и **Vote Share MAE**. Если вероятности недоступны, эти метрики считаются неприменимыми и не заменяются псевдооценками.

## Hypotheses

В работе проверяются три основные гипотезы:
- **H1:** решения LLM- и Decision-подходов демонстрируют положительную согласованность с решениями профессиональных судей;
- **H2:** степень согласованности с профессиональными судьями различается между LLM- и Decision-подходами;
- **H3:** устойчивость решений различается между LLM- и Decision-подходами.

## Reproducibility and Error Handling

Сохраняются все сырые ответы моделей, используемые промпты, версии входных данных, параметры запусков и технические ошибки. Повторная техническая попытка допускается только с тем же входом, промптом и настройками. Успешный ответ не запрашивается повторно из-за его расхождения с оценками судей.

Если для поединка не удалось получить полный комплект из девяти вызовов, он считается неполным и не включается в основные метрики согласованности для этой модели. Пилотные и основные результаты хранятся отдельно; после утверждения финального протокола любые изменения моделей, промптов и параметров документируются.
